# DESIGN — fastapi-asopetrol-reference

Small, complete API deployable on AWS: **FastAPI + SQLAlchemy 2 + PostgreSQL**, tests, containers, infrastructure as code, a queue and cron. Original domain; no client code or data.

**Revision 3 (2026-11-14):** stack migrated from Flask to **FastAPI**. Infrastructure, domain and session design are unchanged; the application layer and the way it is learned change.

---

## 1. Goal

Demonstrate what a backend interview asks about — API, database, migrations, tests, containers, CI/CD, IaC, networking, secrets, queues and observability — **and be able to explain every line of code**.

That is why the project is written by hand, without templates: the goal is understanding, not speed.

## 2. Stack

| Piece | Choice | Why |
|---|---|---|
| Framework | **FastAPI** | Typed validation, dependency injection, automatic OpenAPI |
| Validation | **Pydantic v2** | Schemas are the contract: if the data does not comply, it does not get in |
| ORM | **SQLAlchemy 2.0 (sync)** | One mental model; async is deferred to an ADR |
| Migrations | **Alembic** | Same as before, but with explicit `target_metadata` |
| Driver | **psycopg 3** | Current standard for Postgres |
| Server | **uvicorn** (local) · **gunicorn + uvicorn workers** (container) | |
| Tests | **pytest + httpx/TestClient** | ASGI client, no server to boot |
| Quality | **ruff** | Lint and format |

## 3. Structure

```
src/app/
├── domain/                 pure business rules: no FastAPI, no SQLAlchemy, no I/O
│   └── exceptions.py       DomainError and its subtypes
├── application/            use cases: orchestrate domain and infrastructure
├── infrastructure/         replaceable details
│   ├── config/settings.py  Settings with pydantic-settings (validated env, cached)
│   └── observability/      structlog: JSON logs, one format for everything
└── interface/api/          FastAPI: whatever touches HTTP
    ├── app.py              create_app() + error handlers
    ├── dependencies.py     injectable dependencies (api key, database session)
    └── routes/health.py    /healthz
tests/
└── conftest.py             test app with an isolated database
```

**Layer rule:** dependencies point inward. `interface` knows `application`; `application` knows `domain`; `infrastructure` implements what `application` and `domain` declare. The domain **does not import** FastAPI, SQLAlchemy or anything from the other layers: if that stops being true, the architecture is decorative.

**Where each thing goes:**

| If you are writing… | It goes in |
|---|---|
| A rule that decides something (capacity, idempotency, state) | `domain/` |
| A complete business operation | `application/` |
| SQL, HTTP, email, configuration, logs | `infrastructure/` |
| Routes, request/response schemas, status codes | `interface/` |

## 4. Domain

| Table | Columns |
|---|---|
| `members` | id, email (unique), name, created_at |
| `events` | id, title, starts_at, capacity, status, created_at |
| `registrations` | id, member_id (FK), event_id (FK), status, idempotency_key (unique), created_at |

Constraints: `UNIQUE (event_id, member_id)`, `UNIQUE (idempotency_key)`, indexes on `registrations(event_id)` and `events(starts_at)`.

## 5. API

| Method | Route | What it demonstrates |
|---|---|---|
| GET | `/healthz` | 200 + database status |
| GET | `/members?page=&size=&q=` | Pagination and filters |
| POST | `/members` | Pydantic rejecting invalid data; 201 and 409 |
| GET | `/events` | Listing |
| POST | `/events/{id}/registrations` | Concurrency, idempotency |
| GET | `/reports/events` | CTE + `RANK()` for occupancy |
| GET | `/docs`, `/openapi.json` | **Generated by FastAPI** from the schemas |

**Auth:** a `require_api_key` dependency reading the `X-API-Key` header with `Header(...)`.
**Errors:** domain exceptions caught by handlers → `application/problem+json`.
**Tracing:** middleware that adds `X-Request-Id` and includes it in the logs.

**On OpenAPI:** it is no longer written by hand. A test calls `app.openapi()` and asserts that every route is documented. That teaches how the framework works internally.

## 6. Concurrency (the technical core)

In the `application/` use case that registers a member for an event, inside a single transaction:

1. `SELECT ... FOR UPDATE` on the event row.
2. Count confirmed registrations and compare with `capacity`.
3. Insert if there is room; otherwise raise `NoCapacity` (→ 409).

`UNIQUE (event_id, member_id)` is the last line of defence.

**Test:** `scripts/concurrency_check.py` fires 10 threads at the last remaining seat; exactly `capacity` registrations must survive.

## 8. Planned ADRs

1. FastAPI instead of Flask (typed validation, automatic OpenAPI).
2. SQLAlchemy **sync** instead of async: simplicity and driver; async is documented instead.
3. ECS Express Mode instead of App Runner (closed to new accounts since 2026-04-30).
4. No NAT Gateway: public subnet with a restricted SG for the demo; private subnets + endpoints in production.
5. Terraform state kept locally, and when to migrate it to the S3 backend.
6. Idempotency by header, with `UNIQUE` as the last line of defence.
7. SQS + DLQ versus a hand-rolled worker.
8. Postgres versus DynamoDB: when I would use each one (without adding DynamoDB to the demo).

## 9. Session plan

> Important change: writing everything by hand on a new framework splits session 1 into **two**. That is the price of understanding it, and it is worth paying.

| Session | Deliverable | Definition of done |
|---|---|---|
| **1a** | Environment, app factory with `/healthz`, settings, `/docs` working | `uvicorn` responds and the docs generate themselves |
| **1b** | Database session, models, schemas, member POST/GET, tests | `pytest` green against an isolated database |
| **2** | Registration use case with locking, idempotency, reports, Dockerfile, compose | `docker compose up` + `concurrency_check.py` with no overselling |
| **3** | CI + Terraform (VPC, RDS, S3, Secrets) | `terraform plan` clean |
| **4** | ECS Express + OIDC + `/healthz` + logs + alarm | Public URL responding |
| **5** | SQS + Lambda + cron + ADRs + screenshots + `destroy` | Eight ADRs and the environment destroyed |

## 10. Testing

- Schemas: invalid data returns 422 (Pydantic) and never reaches the database.
- Use cases: capacity and idempotency, without HTTP.
- API: `TestClient` against an isolated database.
- Contract: `app.openapi()` covers every route.
- `/healthz` reports a downed dependency.
- Concurrency: script against the real API with Postgres.

## 11. Acceptance criteria

1. Clone + `docker compose up` → API with seeded data.
2. `make test` and `make lint` green.
3. CI blocks the merge when it fails.
4. `terraform apply` / `destroy` working.
5. `/docs` reflects the real API, with no hand-written YAML.
6. No secrets in the repository.
7. An `EXPLAIN ANALYZE` of the window report.
8. README with architecture, network diagram, ADRs and costs.

## 12. Out of scope

Kubernetes, microservices, an elaborate frontend, multi-region, DynamoDB, Step Functions, Cognito, async SQLAlchemy and any client data.
